# Precision and hardware · 0.6.0

Coordinates retain BigDecimal centre/span values, with approximate double accessors for compatible code. Navigation and pixel/subpixel mapping use decimal arithmetic. Schema-1 projects with only three double fields acquire exact decimal values on load. A positive span may underflow its approximate double without losing the exact span. Centre magnitudes remain within the finite double range; decimal inputs have a 10,000-digit resource limit.

0.10 changes the selection policy: PrecisionController starts Automatic at Double and honours an explicitly selected higher minimum. It no longer promotes from ULP thresholds, coordinate-magnitude bit estimates or iteration margins. CoordinateRegistry checks actual represented sample coordinates while tiles are processed, before CPU/GPU numerical dispatch. Each axis uses a synchronized HashMap from represented value to first axis sample index, with atomic checked-position flags. Repeated x in different rows is legitimate; two distinct x indices mapping to the same value trigger a collision. Imaginary coordinates are checked independently. DD and QD keys use the exact decimal sum of their represented components. Arbitrary keys use the selected decimal rounding. Nonfinite/unrepresentable coordinates also require escalation.

RenderEngine cancels the failed pass, serializes a reset notification against tile publication and retries Double → DD → QD → arbitrary. Old workers cannot publish into the next pass. DocumentRenderer clears prior tiles/previews, updates its completion count for the new tile size and only caches the completed replacement. Final samples and antialiasing subpixels are never deduplicated or skipped. Registry memory is proportional to the two factored axes, not all complex pixels. It is per render/pass, so unrelated views do not inherit a permanently higher precision.

The HashMap criterion checks coordinate uniqueness, not the accuracy of a long chaotic recurrence. Explicit precision selection is available when greater orbit accuracy is desired. Existing reference-orbit error checks and accurate per-sample fallback remain active when perturbation is used.

Double-double uses error-free TwoSum and FMA residual products. Quad-double uses four-component expansion arithmetic, compression and iterative division. Arbitrary precision uses BigDecimal with selected guard digits. All three supported formula families have wide-arithmetic implementations. These are finite numerical methods, not proofs of infinite-orbit membership. A spacing check alone cannot bound a chaotic orbit forever.

For quadratic Mandelbrot at spans at least 1e-280, an optional high-precision reference supports delta recurrence dz' = 2Z dz + dz² + dc. Reference rounding and propagated delta errors are tracked; uncertain bailout, cancellation, exhausted reference or inaccurate smoothing triggers an individual arbitrary-precision recalculation. Smaller spans use direct arbitrary arithmetic. Conservative error tests are engineering safeguards, not a formally verified interval-arithmetic proof. Reference orbits use a bounded 32 MiB LRU. There is no FloatExp or series approximation path.

CPU defaults to Runtime.availableProcessors(), refreshed for automatic renders. Shared atomic tile queues balance expensive regions with worker-local numerical buffers. The existing scan orders and coarse previews remain available. Manual pools support up to max(256, twice detected cores); active workers are limited by tile count. Cancellation is cooperative. Numerical caches are bounded by a heap-aware sample budget, at most 32 million samples and approximately 35% of max heap, plus separate image/temporary buffers; individual layers remain limited to 16 million samples. More threads are not assumed faster: compare the included 1/4/9-worker benchmarks.

GPU probing is asynchronous. OpenCL GPU reports include name/vendor, API, FP64 capabilities, compute units, global memory and allocation limit. Linux without a registered ICD keeps CPU compute; optional aeternalis.forceOpenCLProbe enables a direct-loader probe. Windows uses read-only CIM graphics inventory when compute is unavailable. A graphics name or loader alone is not proof of usable compute.

JOCL 2.0.5 compiles the bundled OpenCL 1.2 FP64 kernel without fast-math. Only Double Mandelbrot and Julia with supported iteration limits qualify. Required rounding/subnormal support is checked. Runtime grids are compared with CPU calculations and arbitrary-precision reference samples, using a 2e-7 smooth-value tolerance. Ambiguous near-bailout samples return to CPU. A transfer-inclusive warm-up/median tile benchmark requires a measured advantage above 10% for Automatic; compilation time is separately recorded. Automatic can let CPU workers consume tiles while one GPU tile is in flight. This heuristic does not guarantee the fastest strategy for every scene.

GPU preferred means GPU where compatible plus safe CPU fallback, never a precision downgrade. Unsupported formulas/precision or runtime failure retain CPU correctness. Resources are released on ordinary failures; a driver stuck inside a native call cannot be guaranteed interruptible. OpenCL execution was NOT available on this validation host, so its conditional test was skipped and GPU/hybrid speed is unmeasured. Vulkan Compute and GPU DD/QD/AP are not implemented.

Performance diagnostics include logical/active workers, precision/reason, selected backend, GPU report, pixels/s, elapsed time, layer-cache hits, escalation count, perturbation attempts/fallbacks and estimated heap/sample budget. Counters are lightweight render aggregates, not a device profiler.

0.9.1 progressive display: wide precision uses 16×16 final tiles (Double remains 64×64). Preview passes start at step64 and refine to step2, publishing immutable partial snapshots about every 0.5 seconds between completed samples. Uncomputed preview cells are explicitly marked and do not overwrite earlier computed pixels. Document composition targets 0.75 seconds between partial images, on its background coordinator. These are best-effort intervals, not guaranteed deadlines during a long single orbit/reference or colour pass. Only complete numerical tiles enter the reusable final cache and completion accounting.
